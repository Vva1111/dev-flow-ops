# TECH_STACK — 기술 선택과 이유

이 문서는 대화에서 선택한 Hono, Node.js, SQLite, Drizzle ORM, node:sqlite와 서버 관리·웹 배포 방향을 기록한다. 다른 기술의 선택 근거는 이후 추가한다. 결정 이력과 미확정 사항은 [DECISIONS.md](DECISIONS.md)를 따른다.

이 문서는 AI의 추천과 설명을 검토한 뒤, 개발자가 직접 선택하고 확정한 기술과 그 이유를 기록합니다.

## 백엔드 API 프레임워크: Hono

- 결정일: 2026-11-03
- 상태: 선택 확정, 도입 및 API 구현 전
- 적용 대상: `apps/finance-server`와 `apps/platform-server`의 HTTP API. 같은 모노레포에서 앱별 `package.json`을 가진 워크스페이스 패키지로 관리한다. 서버 컨테이너·배포 단위는 별도 결정한다.

### 선택 배경

개발자의 주된 목표는 프론트엔드와 CI/CD 역량을 확장하고, 개발·테스트·배포·품질 검증을 연결하는 플랫폼을 완성하는 것이다. 백엔드는 Finance 앱의 실제 동작과 전체 자동화 흐름을 검증할 수 있도록 필요한 기능을 제공해야 한다.

기존 문서의 Fastify 추천을 확정 사항으로 이어받지 않고, 백엔드 학습·구현 부담과 프로젝트 목표를 기준으로 다시 검토한 뒤 Hono를 선택했다.

### 선택 이유

1. **기존 TypeScript 경험을 활용할 수 있다.** Hono는 TypeScript와 웹 표준 `Request`·`Response`를 지원한다. 프론트엔드에서 익힌 HTTP 개념을 활용해 API를 구현하기 좋다고 판단했다.
2. **작은 API부터 시작하기 좋다.** Finance 앱의 거래·카테고리 CRUD와 집계 API를 라우트와 함수 중심으로 구현할 수 있다. 초기부터 복잡한 백엔드 구조를 도입하는 부담을 줄이고, 프론트엔드·테스트·CI/CD에 집중하려는 목적에 맞는다.
3. **API 테스트를 자동화하기 좋다.** `app.request()`로 네트워크 포트를 열지 않고 요청·응답을 검사할 수 있다. Vitest 기반 API 테스트를 CI에 연결하고, 실제 서버와 브라우저를 거치는 흐름은 Playwright로 별도 검증하는 구성을 목표로 한다.
4. **배포 환경을 변경하기 비교적 쉽다.** Node.js뿐 아니라 여러 실행 환경을 지원하므로 API 코드를 재사용하며 배포 환경을 옮기기 좋다. 현재 OCI·Docker 운영 목표를 유지할 수 있고, 다른 환경으로의 이전 가능성도 남긴다. 다중 환경 지원은 부가적인 장점이며, 여러 환경에 동시에 배포하는 것을 목표로 삼지는 않는다.

### 감수할 점과 남은 결정

- ORM과 SQLite 드라이버는 아래 Drizzle 및 node:sqlite 항목에서 별도로 확정했다. 백엔드 런타임은 Node.js로 확정했으며 저장소의 고정 버전을 따른다. 웹/서버는 별도 워크스페이스로 관리한다. 검증 라이브러리와 서버 컨테이너·배포 구성은 별도 결정한다.

### 선택의 핵심

필요한 백엔드 API를 작게 구현하고, 프로젝트의 핵심인 프론트엔드 개발과 검증·배포·품질 추적 흐름을 완성하는 데 집중하기 위해 Hono를 선택했다.

## 데이터베이스: SQLite

- 결정일: 기존 확정 사항 (선택 이유 정리: 2026-11-03)
- 상태: 선택 확정, DB 도입 및 스키마 구현 전
- 적용 대상: 검증용 Finance 앱의 거래·카테고리 데이터. 플랫폼 실행 이력의 저장 방식은 별도 결정한다.

### 선택 배경

별도의 DB 서버를 운영하는 부담을 줄이고, 파일 기반 DB로 간단하고 가볍게 구현하기 위해 SQLite를 선택했다. Finance 앱에 필요한 데이터 저장·조회·집계 기능을 제공하면서 프론트엔드·테스트·CI/CD 흐름 구현에 집중하려는 목적이다.

소규모 Finance 앱과 단일 OCI 서버에서 앱과 DB 파일을 함께 운영하는 현재 목표를 기준으로 적합하다고 판단했다. 실제 OCI 인스턴스 확보와 배포 검증은 아직 완료하지 않았다.

### 선택 이유

1. **별도 DB 서버 운영이 필요 없다.** 애플리케이션에서 라이브러리를 통해 DB 파일에 접근하므로 DB 서버 프로세스를 따로 설치·구성·운영하는 부담을 줄일 수 있다.
2. **파일 기반으로 데이터를 관리할 수 있다.** 데이터를 기본적으로 하나의 DB 파일에 저장한다. 다만 실행 중에는 저널 등 보조 파일이 생길 수 있으며, 백업은 실행 상태와 설정을 고려해 수행해야 한다.
3. **Finance 앱에 필요한 관계와 집계를 구현할 수 있다.** SQL을 사용해 거래와 카테고리의 관계, 기간별 조회, 수입·지출 집계를 구현할 수 있다. 단순한 저장 구성으로도 API·DB 연동을 포함한 실제 기능을 검증할 수 있다.
4. **테스트 데이터를 분리하기 좋다.** 테스트용 DB를 별도로 생성하고 시드 데이터를 넣어 검증하는 구성을 만들 수 있다. 운영 DB를 변경하지 않고 단위·통합·E2E 테스트와 CI를 재현 가능하게 구성하는 데 활용한다.

### 감수할 점과 남은 결정

- DB 파일 하나에 동시에 하나의 쓰기만 가능하다. 쓰기 요청이 많아지거나 여러 서버에서 같은 데이터를 처리해야 한다면 DB 선택과 접근 구조를 재검토한다.
- Docker 컨테이너 교체 시에도 데이터가 남도록 영속 볼륨을 구성하고, 백업·복원 절차와 파일 접근 권한을 정해야 한다. 실사용 DB를 Git이나 Docker 이미지에 포함하지 않는다.
- ORM과 SQLite 드라이버는 아래 Drizzle 및 node:sqlite 항목에서 별도로 확정했다. 스키마, 제약조건, 마이그레이션, 저널 모드와 잠금 대기 설정은 별도 결정한다.
- 운영은 읽기 전용 Smoke Test를 사용하고, 데이터 변경 테스트는 격리된 테스트 DB·환경에서 수행한다.
- 실제 앱의 처리 성능과 동시성은 아직 측정하지 않았다. 단순한 운영 구성에 대한 적합성 판단이며 성능 개선을 입증한 결과는 아니다.

### 선택의 핵심

별도 DB 서버 없이 파일 기반으로 필요한 데이터 기능을 구현하고, DB 운영 부담을 줄여 프론트엔드 개발과 테스트·CI/CD 흐름에 집중하기 위해 SQLite를 선택했다.

- [파일 기반 저장과 이식성](https://www.sqlite.org/onefile.html)

## ORM: Drizzle ORM

- 결정일: 2026-11-03
- 상태: 선택 확정, 도입 및 DB 연동 구현 전
- 적용 대상: Finance 앱의 SQLite 데이터 접근. 플랫폼 실행 이력의 저장 방식은 별도 결정한다.

### 선택 배경

DB와 ORM에 익숙하지 않은 프론트엔드 개발자로서, 필요한 데이터 기능을 구현하면서 프론트엔드와 CI/CD에 집중할 수 있는 도구를 원했다. SQL을 배우는 과정과 동떨어진 사용법을 익히기보다, SQL과 비슷한 형태로 조회·저장 코드를 작성하고 익숙한 TypeScript의 도움을 받을 수 있다는 설명을 검토한 뒤 Drizzle을 선택했다.

### 선택 이유

1. **SQL을 배우면서 함께 익히기 좋다.** SQL 방식의 쿼리 API는 `select`, `from`, `where`처럼 SQL 구조와 유사하다. SQL 개념을 코드와 연결하기 좋다고 판단했다. 다만 SQL 문법을 그대로 쓰는 것은 아니며, 조건 함수와 테이블 정의 등 Drizzle 사용법은 배워야 한다.
2. **익숙한 TypeScript의 도움을 받을 수 있다.** 테이블 구조를 TypeScript로 정의하고 조회·저장에 필요한 타입을 추론할 수 있다. 자동완성과 타입 검사를 활용해 테이블·컬럼을 다루는 실수를 줄이는 데 도움을 받을 수 있다.
3. **별도의 ORM 클라이언트 생성 단계가 필수가 아니다.** 테이블 구조를 정의한 TypeScript 코드를 직접 활용하므로, DB 구조에 맞는 클라이언트 코드를 생성하고 갱신하는 단계를 따로 관리하지 않아도 된다. 애플리케이션의 TypeScript 빌드·타입 검사와 DB 마이그레이션은 별개다.
4. **선택한 SQLite와 함께 사용할 수 있다.** SQLite용 드라이버와 연결해 거래·카테고리 데이터에 접근할 수 있다. API는 Hono, 데이터 접근은 Drizzle, 실제 저장은 SQLite가 담당하는 구성을 목표로 한다.

### 감수할 점과 남은 결정

- SQL, 제약조건, 관계, 트랜잭션과 마이그레이션의 기본 개념은 배워야 한다. 학습 부담이 없거나 모든 API가 SQL과 1:1 대응한다고 가정하지 않는다.
- Drizzle은 데이터 접근을 감싸고 SQL을 생성하는 라이브러리다. ORM 클라이언트 코드 생성이 필수가 아니라는 것이 ORM 계층 자체가 없다는 뜻은 아니다.
- SQLite 드라이버는 아래 node:sqlite 항목에서 별도로 확정했다. Drizzle 패키지 버전, 스키마, 마이그레이션 도구·실행 절차는 별도 결정한다. Drizzle Kit은 마이그레이션 생성·적용을 돕는 별도 도구이며, 이번 ORM 선택만으로 도입을 확정하지 않는다.
- 타입 검사가 HTTP 입력의 런타임 검증을 대신하지 않는다. DB 영속 볼륨, 백업·복원과 운영·테스트 DB 분리도 별도 구현해야 한다.
- 학습 시간과 개발 생산성 개선은 아직 측정하지 않았다. 선택 이유는 대화와 공식 문서에 근거한 적합성 판단이다.

### 선택의 핵심

SQL과 유사한 API를 통해 SQL을 배우면서 필요한 DB 기능을 구현하고, 익숙한 TypeScript의 자동완성과 타입 검사를 활용하기 위해 Drizzle을 선택했다. 별도의 ORM 클라이언트 코드를 생성·갱신하는 단계가 필수가 아니라는 점도 선택 이유다.

## SQLite 드라이버: node:sqlite

- 결정일: 2026-11-03
- 상태: 선택 확정, Drizzle 연동 및 대상 환경 검증 전
- 적용 대상: Node.js에서 실행하는 Finance API의 로컬 SQLite 접근

### 선택 배경

백엔드 런타임을 Node.js로 선택한 뒤, 별도 드라이버 패키지의 설치와 관리를 줄이기 위해 Node.js 내장 모듈인 `node:sqlite`를 선택했다. 현재 고정된 Node.js 버전에서 RC 상태라는 설명을 검토한 뒤 의존성을 줄이는 방향을 우선했다.

### 선택 이유

1. **외부 드라이버 패키지를 추가하지 않아도 된다.** Node.js에 포함된 모듈을 사용하므로 `better-sqlite3`나 `@libsql/client`를 별도 설치·관리할 필요가 없다. Drizzle ORM 자체는 별도 의존성으로 필요하다.
2. **선택한 실행 환경과 맞는다.** Node.js와 로컬 SQLite 파일을 사용하는 현재 목표에 맞춰 구성할 수 있다. 드라이버를 위해 별도의 네이티브 패키지를 설치·빌드하는 부담을 줄이는 방향이다.
3. **Drizzle과 연결할 수 있다.** 공식 문서에 `drizzle-orm/node-sqlite` 연결 방식이 안내되어 있다. 실제 사용할 Drizzle 버전에서 지원 여부와 동작을 확인한 뒤 구현한다.

### 감수할 점과 남은 결정

- 현재 고정한 Node.js 24.22.2에서 `node:sqlite`는 RC(Release Candidate) 상태다. 향후 안정화 시점이나 API 변경 여부를 보장하지 않으며, Node.js 업데이트 시 호환성을 확인해야 한다.
- Node.js 고정 버전과 사용할 Drizzle 버전의 조합, Windows 및 Linux/ARM64 환경에서의 실행은 아직 검증하지 않았다. 드라이버 선택이 RC 버전의 Drizzle 패키지 도입까지 승인한 것은 아니다.
- 동기식 DB 작업은 실행 중 Node.js 이벤트 루프를 점유한다. 긴 쿼리와 동시 요청 처리의 영향은 구현 후 확인해야 한다.
- 마이그레이션 구성, 영속 볼륨과 백업·복원은 별도로 마련한다. 내장 드라이버 사용이 데이터 보존 문제까지 해결하지는 않는다.
- 의존성을 줄이려는 설계 선택이며 설치 시간, 이미지 크기와 성능의 개선은 아직 측정하지 않았다.

### 선택의 핵심

Node.js 내장 SQLite 모듈을 사용해 별도 드라이버 패키지의 설치·관리 부담을 줄이기 위해 node:sqlite를 선택했다. 현재 RC 상태와 연동 검증이 남아 있다는 점을 인지하고 선택했다.

- [Node.js 24의 SQLite 모듈과 안정성 상태](https://nodejs.org/docs/latest-v24.x/api/sqlite.html)

## 백엔드 런타임: Node.js

- 결정일: 2026-11-03
- 상태: 선택 확정, 서버 실행 구성 전
- 적용 대상: Finance와 플랫폼 백엔드. 저장소에 고정된 Node.js 24.22.2를 사용한다.

### 선택 배경

사용자가 백엔드 런타임으로 Node.js를 직접 선택했다. 현재 저장소의 개발 도구도 Node.js를 사용하며 Hono 서버와 Finance의 내장 SQLite 모듈을 이 환경에서 실행하는 구성을 목표로 한다.

### 선택 이유

1. **TypeScript 기반 서버를 구성할 수 있다.** Hono와 Drizzle을 사용하는 백엔드를 Node.js에서 실행하는 방향을 선택했다.
2. **내장 SQLite 모듈을 활용할 수 있다.** 이후 드라이버 결정에서는 `node:sqlite`를 선택해 별도 드라이버 의존성을 줄이기로 했다.
3. **실행 환경 버전을 통일한다.** 기존 `.nvmrc`와 루트 `package.json`의 고정 버전을 개발·CI·Docker에서도 따르도록 한다.

### 감수할 점과 남은 결정

- 두 서버의 `package.json`과 실행·빌드 설정은 아직 없다. TypeScript 실행·빌드 방식과 패키지 버전은 구현 시 결정한다.
- `node:sqlite`의 RC 상태, Drizzle 버전 호환성과 Windows 및 Linux/ARM64 실행은 검증 전이다. 플랫폼 결과 저장소는 아직 선택하지 않았다.

### 선택의 핵심

백엔드를 Node.js에서 실행하고, 같은 저장소의 고정 버전과 내장 SQLite 모듈을 활용하는 방향으로 구성한다.

## 서버 관리 구조와 웹 배포 방향

- 결정일: 2026-11-03
- 상태: 모노레포 관리·명칭·웹 앱별 배포 방향 선택, 서버는 폴더 구조만 생성
- 적용 대상: `finance-web`, `finance-server`, `platform-web`, `platform-server`

### 선택 배경

기존 모노레포의 앱별 `package.json` 관리 방식을 백엔드에도 적용하기로 했다. 백엔드는 HTTP API 외에도 비즈니스 로직과 데이터 접근을 담당하므로 이름을 `server`로 정했다. 두 프론트엔드는 각각의 Nginx에서 별도 배포하는 방향을 선택했다.

### 선택 이유

1. **같은 저장소에서 작업하면서 앱별 책임을 구분한다.** 의존성과 작업 명령은 각 앱이 관리하고, 루트 pnpm/Turborepo는 전체 작업을 실행한다.
2. **서버가 소유하는 범위를 드러낸다.** Finance 서버는 금융 도메인·DB 접근·마이그레이션을, 플랫폼 서버는 GitHub 연동과 실행 결과 연결을 담당한다. 플랫폼 실행 메타데이터와 금융 데이터를 분리한다.
3. **프론트엔드를 앱별로 배포한다.** Finance와 포털을 하나의 공통 웹 컨테이너에 묶지 않고 각각의 Nginx 컨테이너로 배포하는 방향이다. 테스트도 앱별 대상 주소·배포 버전을 기준으로 연결한다.

### 감수할 점과 남은 결정

- 두 서버는 README와 `.gitkeep`으로 폴더 구조만 준비했으며, `package.json`과 실행 코드는 없다. 현재 pnpm/Turborepo 명령은 기존 두 프론트엔드만 대상으로 한다.
- 서버 컨테이너 구성과 도메인·HTTPS·네트워크 범위·포트·프록시·인증은 미확정이다. 컨테이너 간 API 통신은 Docker 네트워크를 활용하는 방향이며, 브라우저는 내부 서비스 이름으로 직접 접근하지 않는다.
- Finance 운영 DB는 소스·이미지 밖의 영속 볼륨에 둔다. 플랫폼 저장 방식과 DB 폴더는 아직 정하지 않았다.
- 개발 시간과 운영 효율의 개선을 직접 측정한 결과는 아니다.

### 선택의 핵심

프론트엔드와 백엔드를 하나의 모노레포에서 앱별로 관리하고, Finance와 포털 프론트엔드는 별도 Nginx로 배포한다. 소스 패키지 분리와 서버 컨테이너 구성은 별개의 결정이다.
