# DECISIONS — 확정 사항과 변경 가능한 선택

이 문서는 Codex가 과거의 제안/가정을 확정 사항으로 잘못 받아들이지 않도록 돕는 결정 로그다. **구현 상태가 아닌 설계 의사결정의 상태**를 나타낸다.

상단 표는 현재 결정 상태이며, 날짜별 기록의 보류·미확정 표현은 당시 상태다. 이후 결정으로 대체된 기록은 이력으로 유지한다. 현재 구현 상태는 [개발 진행 현황](DEVELOPMENT_STATUS.md), 실행한 검사와 미확인 항목은 [검증 기록](DEVELOPMENT_GUIDE.md#6-현재-검증-상태)을 따른다.

## 2026-11-14 — PR CI와 자동 병합 운영

- main 변경은 작업 브랜치와 PR을 거치며 필수 CI 통과 후 자동 병합한다. Draft PR은 병합하지 않고 ready 전환 시 CI를 다시 실행한다. 다른 사람의 리뷰 승인은 필수로 두지 않는다.
- 자동 병합은 같은 저장소의 OWNER·MEMBER·COLLABORATOR PR에 적용하고 squash 방식으로 수행한다. 포크 PR은 CI만 수행한다. 실행 시 최신 커밋과 Draft 상태를 다시 확인한다.
- CI는 읽기 권한으로 실행하고 병합 워크플로는 PR 코드나 Artifact를 실행하지 않는다. 저장소의 자동 병합 허용과 main 필수 검사·직접 push 및 강제 push 차단은 GitHub에서 별도 적용해야 한다. 현재 설정 적용 여부는 미검증이다.

## 변경 관리 원칙

- 목표·우선순위 변경은 [개발 목표 유지 기준](PROJECT_CONTEXT.md#개발-목표-유지-기준)에 따라 사용자 합의를 확인하고 현재 결정과 이력에 반영한다.
- 상위 목표(D-02)와 비용 제약(D-10)을 유지한 채 세부 기술은 바꿀 수 있다.
- 기술 변경 시 이유, 검증한 대안, 영향, 결정 날짜를 여기에 추가한다.
- AI가 제안하는 개선/실행 결과는 결정된 기술 선택을 자동으로 뒤집지 않는다.
- 프로젝트의 최우선 엔지니어링 결과는 재현 가능한 개발·빌드·테스트·배포 프로세스다.

## 2026-11-12 — 번역 JSON의 최대 3단계 분류

- 사용자가 각 언어 JSON을 최대 3단계 깊이로 분류하도록 요청했다. 이전 평면 키 방식을 대체하고 common과 기능별 중첩 객체로 구성한다.
- 앱별 파일에 중복되는 finance·portal 접두사는 제거하고, i18next의 점 구분 경로 조회를 사용한다. 번역 문구·보간·복수형과 사용자 데이터는 유지한다.
- 작성 규칙과 검증 결과는 개발 가이드에서 관리한다.

## 2026-11-12 — 의미 기반 번역 키 전환

- 사용자가 한글 문장 키를 의미 기반 키로 바꾸도록 요청했다. Finance와 포털에 같은 작성 규칙을 적용하고 기존 한국어 원문 키 사용 방식을 대체한다.
- 화면·오류·성공 안내·앱 유형·문서 제목의 참조를 함께 전환하며, 번역 문구·보간·복수형과 사용자 데이터는 유지한다. 별도 번역 서비스나 새 의존성은 도입하지 않는다.
- 구체적인 작성 규칙과 검증 결과는 개발 가이드에서 관리한다.

## 2026-11-12 — 포털 관리 앱 자동 발견

- 사용자가 apps에 추가한 앱을 포털 목록에 자동 반영하도록 요청했다. 현재 워크스페이스 범위의 package.json을 기준으로 웹·서버·포털 패키지를 함께 발견하는 방향을 선택했다.
- 앱 식별자는 워크스페이스 이름을 사용하며 서버 연동이나 인증·실행 권한 구조를 새로 도입하지 않는다. 실행 대상 등록 계약은 후속 설계로 유지한다.
- 개발 절차와 표시 규칙은 [개발 가이드](DEVELOPMENT_GUIDE.md#9-포털-관리-앱-자동-발견)를 따른다.

## 2026-11-12 — 전체 파이프라인 목표와 우선순위 재확인

- 사용자가 전체 파이프라인에 대한 개발 방향을 유지하도록 기존 문서 보완을 요청했다. 목표·범위는 프로젝트 컨텍스트, 실행 흐름·책임은 아키텍처, 작업 시 준수 규칙은 AGENTS.md에서 관리한다.
- 기존 플랫폼 목표를 유지하면서 Finance 기능 확장보다 공통 자동화 연결을 우선하는 기준을 명시했다. 목표를 새로 정의하거나 설계를 구현 완료로 표시하는 변경은 아니다.
- 아키텍처 도식에 AI 없이 기본 결과를 생성·조회하는 경로와 개발자 피드백 경로를 보완했다.

## 2026-11-12 — Finance Playwright 도입 승인

- 사용자가 Playwright 개발 의존성과 브라우저 설치, 브라우저 검증 실행을 승인했다. 패키지는 기존 pnpm과 lockfile로 관리한다.
- 첫 범위는 Finance 핵심 사용자 흐름의 Chromium 데스크톱·모바일 에뮬레이션이다. 기존 개발 서버를 재사용하지 않고 실행별 임시 DB를 사용하는 방향으로 구성한다.
- 실행 절차와 결과는 [개발 가이드](DEVELOPMENT_GUIDE.md#8-finance-브라우저-e2e)를 따른다. 실제 모바일 기기·다른 OS와 브라우저 지원을 검증한 것으로 확대 해석하지 않는다.

## 2026-11-10 — Finance 화면 API 연결

- 수입·지출 목록과 등록·수정·삭제를 기존 API에 연결했다. API 요청과 상태, 폼·목록은 finance-web의 `src/features/transactions`가 소유하며 새 의존성은 추가하지 않았다.
- 성공 응답을 받은 뒤 목록을 갱신하고 실패하면 폼 입력을 유지한다. 로딩·조회 실패·빈 목록·변경 중 상태, 삭제 확인과 조회 재시도를 제공한다. 중복 변경 요청을 제한하고 초기 조회는 언마운트 시 취소한다.
- 월별 수입·지출과 소비 분포는 조회 내역 중 브라우저의 현재 월에 해당하는 기록으로 계산한다. 금액 합계는 BigInt로 계산하며 목록의 종류 필터는 월별 합계에 영향을 주지 않는다.
- 자산·부채·예산·저축 목표는 샘플 표시를 유지한다. 서버에 없는 계좌·이체 항목은 입력과 내역 필터에서 제거했다.
- 화면 소스·Vite 설정 타입 검사와 lint를 통과했고 임시 DB를 대상으로 Vite 프록시의 CRUD 응답을 확인했다. 브라우저에서 폼·버튼·새로고침을 직접 실행하는 검증, 테스트·빌드 명령은 수행하지 않았다.

- 사용자가 관리 포털의 백엔드도 `apps/platform-server`에 구성하기로 결정했다. 기존 `apps/platform-api` 권장 경로를 대체한다.
- Finance 서버와 같은 모노레포 안의 별도 워크스페이스 패키지로 관리한다. 현재는 조회 API, GitHub 연동, 결과 처리 코드의 폴더 구조와 안내 문서만 추가했다.
- 실행 코드·`package.json`·의존성은 추가하지 않았다. 실행 이력 저장소와 인증, GitHub 동기화 계약, 컨테이너·배포 구성은 미확정이다.

## 2026-11-03 — 웹 앱별 배포 방향과 현재 구조 정리

- 대화에서 Finance와 포털 프론트엔드를 각각의 Nginx 컨테이너로 별도 배포하는 방향을 선택했다. 이전의 공통 Nginx 제안은 채택하지 않았다.
- 컨테이너 간 API 통신은 Docker 네트워크로 구성하는 방향이다. 브라우저는 Docker 내부 서비스 이름으로 직접 통신하지 않으며, 외부 접근 주소와 프록시·인증은 별도 설계한다.
- 서버 컨테이너 통합·분리, 네트워크 범위, 도메인·포트·HTTPS, 마이그레이션과 백업의 세부 방식은 이번 방향 선택만으로 확정하지 않는다.
- 두 서버에 `.gitkeep`과 README로 폴더 구조만 생성했다. Finance의 DB 접근·마이그레이션은 서버 내부에 두고 실제 운영 DB 파일은 소스·이미지와 분리한다. 플랫폼은 저장 방식이 미정이므로 DB 폴더를 만들지 않았다.
