# DECISIONS — 확정 사항과 변경 가능한 선택

이 문서는 Codex가 과거의 제안/가정을 확정 사항으로 잘못 받아들이지 않도록 돕는 결정 로그다. **구현 상태가 아닌 설계 의사결정의 상태**를 나타낸다.

상단 표는 현재 결정 상태이며, 날짜별 기록의 보류·미확정 표현은 당시 상태다. 이후 결정으로 대체된 기록은 이력으로 유지한다. 현재 구현 상태는 [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) G절과 [ARCHITECTURE.md](ARCHITECTURE.md)를 따른다.

## 변경 관리 원칙

- 상위 목표(D-02)와 비용 제약(D-10)을 유지한 채 세부 기술은 바꿀 수 있다.
- 기술 변경 시 이유, 검증한 대안, 영향, 결정 날짜를 여기에 추가한다.
- AI가 제안하는 개선/실행 결과는 결정된 기술 선택을 자동으로 뒤집지 않는다.
- 프로젝트의 최우선 엔지니어링 결과는 재현 가능한 개발·빌드·테스트·배포 프로세스다.

## 2026-11-02 — 초기 개발 구조

- Node.js 24.22.2 LTS와 pnpm 10.34.6을 고정한다. 설치된 Node 24.21.0을 그대로 채택하지 않고 지원 중인 LTS의 패치 버전을 선택했다.
- 근거: [Node 24.22.2 공식 릴리스](https://nodejs.org/en/blog/release/v24.22.2), [pnpm Node 호환표](https://pnpm.io/installation), [Vite Node 요구사항](https://vite.dev/guide/).
- 우선 `apps/finance-web`만 생성한다. API 분리 및 프레임워크/ORM 결정은 보류한다.
- 공통 패키지는 실제 재사용 시점에 생성한다. ESLint 설정은 초기에는 루트에서 관리한다.
- CI 및 Docker 구현 시 동일한 Node/pnpm 버전을 사용한다. 현재 해당 실행 환경은 미구현이다.
- pnpm 10 설정은 `pnpm-workspace.yaml`에서 관리한다. `engineStrict`, `packageManagerStrict`, `packageManagerStrictVersion`으로 설치 시 버전을 검사하고, `managePackageManagerVersions: false`로 pnpm 자동 전환을 끈다. 환경별로 지정 버전을 먼저 설치·선택한다.

## 2026-11-02 — 플랫폼 관리 화면과 단일 모노레포 확장

- 플랫폼 도구와 Finance App은 단일 모노레포에서 함께 개발한다. 저장소 공유가 앱들의 동시 배포를 뜻하지는 않는다.
- 앱별 테스트 실행 요청과 CI/CD·배포 후 QA 결과를 커밋 기준으로 연결하는 별도 관리 화면을 목표 범위에 추가한다. GitHub의 코드 저장·리뷰 및 Actions 실행 기반을 활용한다.
- `apps/platform-web`을 관리 UI의 목표 경로로 둔다. Finance App은 첫 검증 대상이고, 관리 UI는 플랫폼 자체 기능이다.
- 공통 실행·수집·보고를 재사용하되 테스트 시나리오와 앱별 실행 설정은 각 앱이 소유한다. 조회 기능을 먼저 완성한 뒤 제한된 테스트 실행 요청을 추가한다.
- 플랫폼 API의 별도 앱 경로(`apps/platform-api`)는 권장안이다. 프레임워크, 배포 구성, 인증·권한, 저장소, 동기화 및 앱 등록 계약은 미확정이다. 실제 구현 전에 상세 설계한다.
- 운영 배포·롤백 버튼과 범용 CI 엔진은 초기 범위에 포함하지 않는다. 현재 변경은 문서상 목표이며 구현 완료를 의미하지 않는다.

## 2026-11-02 — 개발 포털 기본 뼈대

- `apps/platform-web`에 React + TypeScript + Vite 기반 포털 워크스페이스를 추가한다. 기존 Finance 앱과 동일한 의존성 및 검사 명령을 사용한다.
- 관리 앱, 검증·배포 단계, 실행 이력의 빈 상태를 먼저 제공한다. 표시된 상태는 미연결/미실행이며 실제 실행 결과나 샘플 성공 수치가 아니다.
- 포털 개발 포트는 5174, 미리보기 포트는 4174로 고정하여 두 앱을 구분한다.
- 플랫폼 API, 인증, 저장 방식과 GitHub 연동은 보류한다. 테스트 실행 요청은 비활성 상태로 두며 CI/CD 워크플로는 이 단계에서 추가하지 않는다.

## 2026-11-03 — 백엔드 API 프레임워크 확정

- 기존 Fastify 추천안을 재검토한 뒤 사용자가 Hono를 백엔드 API 프레임워크로 확정했다. 이전 날짜의 보류 기록은 당시 상태를 나타낸다.
- 프론트엔드·CI/CD 중심의 목표, TypeScript 경험 활용, 작은 API 구현과 테스트 자동화의 용이성을 선택 기준으로 삼았다. 다중 실행 환경 지원은 부가적인 장점이다.
- Fastify·Express·NestJS와의 비교는 요구사항과 문서에 근거한 검토이며 직접 구현한 비교 실험은 아니다.
- 선택 이유와 한계는 [TECH_STACK.md](TECH_STACK.md)에 기록한다. Hono 설치와 API 구현은 아직 하지 않았다.
- ORM, SQLite 드라이버, 검증 라이브러리, 백엔드 런타임 구성, 웹/API 분리 및 플랫폼 API 배포 구성·인증·저장 방식은 별도 결정한다.

## 2026-11-03 — ORM 확정

- 사용자가 AI의 추천과 설명을 검토한 뒤 Drizzle ORM을 직접 선택·확정했다. 앞선 ORM 보류 기록은 당시 상태를 나타낸다.
- DB·ORM에 익숙하지 않은 프론트엔드 개발자가 SQL을 배우면서 구현하기 좋은 API와 TypeScript 타입 지원, 별도 ORM 클라이언트 코드 생성이 필수가 아닌 구성을 선택 이유로 삼았다.
- 선택 이유와 한계는 [TECH_STACK.md](TECH_STACK.md)에 기록한다. 설치 및 DB 연동 구현은 아직 하지 않았다.
- SQLite 드라이버, 패키지 버전, 스키마와 마이그레이션 도구·실행 절차는 미확정이다. Drizzle Kit 도입은 별도 결정한다.

## 2026-11-03 — 백엔드 런타임 확정

- 사용자가 백엔드 런타임으로 Node.js를 선택·확정했다. 앞선 런타임 보류 기록은 당시 상태를 나타낸다.
- 저장소에 고정된 Node.js 버전을 사용한다. API 실행 구성과 SQLite 드라이버는 아직 구현·확정하지 않았다.

## 2026-11-03 — SQLite 드라이버 확정

- 사용자가 Node.js 내장 `node:sqlite`를 사용해 별도 드라이버 패키지 의존성을 줄이는 방향을 선택했다. 앞선 드라이버 보류 기록은 당시 상태를 나타낸다.
- 현재 고정한 Node.js 24.22.2에서는 RC 상태이며, 안정화 시점과 향후 API 불변성을 보장하지 않는다. 선택 이유와 제약은 [TECH_STACK.md](TECH_STACK.md)를 따른다.
- 실제 사용할 Drizzle 버전의 지원 여부, Windows 및 Linux/ARM64 실행은 검증 전이다. 패키지 설치나 버전 변경은 하지 않았다.
- Drizzle 패키지 버전과 마이그레이션 구성은 별도 결정한다.

## 2026-11-03 — 백엔드 API의 모노레포 관리 확정

- 사용자가 백엔드 API도 현재 모노레포 구조 안에서 관리하는 것으로 확정했다. 기존 앱별 패키지 관리 방식을 백엔드에도 적용한다.
- Finance 프론트엔드는 `apps/finance-web`, API는 `apps/finance-server`에서 각각 별도 `package.json`으로 의존성과 실행·빌드·검증 명령을 관리한다. 루트 pnpm Workspaces와 Turborepo가 전체 작업을 관리한다.
- 선택 이유는 프론트엔드와 백엔드의 실행 환경·의존성을 구분하면서 같은 저장소의 공통 개발 흐름을 유지하기 위해서다.
- 이번 변경은 설계 문서 반영이며 API 패키지는 아직 생성하지 않았다. 컨테이너 통합·분리와 배포 단위는 별도 결정한다.

## 2026-11-03 — Finance 백엔드 명칭 변경

- 사용자가 백엔드 전체의 책임을 드러내기 위해 명칭을 `finance-server`로 변경했다. HTTP API뿐 아니라 비즈니스 로직, DB 접근과 마이그레이션도 이 프로젝트가 소유한다.
- 기존 백엔드 폴더를 `apps/finance-server`로 옮기고 관련 문서의 경로를 맞췄다. 폴더 구조만 있으며 실행 코드와 `package.json`은 아직 없다.
- 컨테이너 구성과 배포 단위는 이번 명칭 변경과 별도로 결정한다.

## 2026-11-03 — 플랫폼 서버 구조 추가

- 사용자가 관리 포털의 백엔드도 `apps/platform-server`에 구성하기로 결정했다. 기존 `apps/platform-api` 권장 경로를 대체한다.
- Finance 서버와 같은 모노레포 안의 별도 워크스페이스 패키지로 관리한다. 현재는 조회 API, GitHub 연동, 결과 처리 코드의 폴더 구조와 안내 문서만 추가했다.
- 실행 코드·`package.json`·의존성은 추가하지 않았다. 실행 이력 저장소와 인증, GitHub 동기화 계약, 컨테이너·배포 구성은 미확정이다.

## 2026-11-03 — 웹 앱별 배포 방향과 현재 구조 정리

- 대화에서 Finance와 포털 프론트엔드를 각각의 Nginx 컨테이너로 별도 배포하는 방향을 선택했다. 이전의 공통 Nginx 제안은 채택하지 않았다.
- 컨테이너 간 API 통신은 Docker 네트워크로 구성하는 방향이다. 브라우저는 Docker 내부 서비스 이름으로 직접 통신하지 않으며, 외부 접근 주소와 프록시·인증은 별도 설계한다.
- 서버 컨테이너 통합·분리, 네트워크 범위, 도메인·포트·HTTPS, 마이그레이션과 백업의 세부 방식은 이번 방향 선택만으로 확정하지 않는다.
- 두 서버에 `.gitkeep`과 README로 폴더 구조만 생성했다. Finance의 DB 접근·마이그레이션은 서버 내부에 두고 실제 운영 DB 파일은 소스·이미지와 분리한다. 플랫폼은 저장 방식이 미정이므로 DB 폴더를 만들지 않았다.
